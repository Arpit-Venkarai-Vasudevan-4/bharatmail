# PhoneMail Requirements and Acceptance Matrix

The original rows retain their earlier-stage classifications. Stage 2 progress and Stage 3 amendments are recorded in the overlays below; the current, evidence-based Stage 3 status is in `VERIFICATION.md` and takes precedence over historical row labels. “Partial” means a local slice exists but the requested behavior is not fully verified. Tests are isolated HTTP/PostgreSQL tests unless marked unit.

## Stage 3 amendments

* **Requirements 46 and 50:** implemented triggering operations now write structured `account_audit_events` for account creation, accepted phone proof, successful login/logout, bounded known-account failed authentication, phone changes, alias lifecycle, security/privacy setting changes, message deletion, session renewal, and detected refresh-credential replay. Relevant high-risk events create durable in-app owner notifications in the same transaction as the operation. Failed authentication coalesces per known account within five minutes; unknown identities create no account-linked event, limiting enumeration and logging abuse. Metadata uses an allowlist and excludes credentials, raw phone numbers, message content, and IP-derived “new device” claims. Operation retries that recover an existing result do not create another success event; retries that actually repeat an operation follow its transaction semantics. Notification-read state is owner-authorized. Retention is bounded operationally by the existing cleanup policy; this is not a legal retention/compliance claim. Migration 029 is additive and fresh/pre-029 upgrade tested.
* Categories with no implemented trigger are intentionally absent: account recovery, administrator action, account deletion, and device recognition/new-device detection are not invented or implied.
* The complete Node 24 acceptance command and current test matrix supersede historical counts and classifications below; see `VERIFICATION.md` and `SUBMISSION_RUNBOOK.md`.

## Stage 3 amendments

* Requirement 8 now includes `POST /api/auth/refresh` for bearer and cookie transports: 15-minute access tokens, 30-day refresh families, and a bounded 90-second encrypted lost-response retry. See `test/session-renewal.integration.test.ts`; this replaces the earlier “no refresh endpoint” status below.
* Requirement 43 extends Stage 2's 10,000-record materialized snapshot with streaming snapshots above that boundary. The final regression reconstructs 12,001 records against PostgreSQL. Streaming snapshots retain a read-only repeatable-read transaction/client, are capped at four per API instance, expire after 15 minutes, and require instance affinity; see `test/large-sync.integration.test.ts`. The Stage 2 10,000-record quota remains the materialized path, not an overall mailbox truncation cap.
* Telecom workflows in requirements 30 and 44 include the local outbox worker and signed SMS/IVR fixtures. The worker-enabled integration is separately run because the default acceptance Compose service disables it. Live provider traffic remains untested.

## Remaining acceptance outside this local Stage 2 implementation

These are external deployment/acceptance boundaries, not unfinished local gates:

1. **Live telecom provider acceptance:** an authorized Twilio account, approved Verify/Messaging services, permitted sender/recipient, production HTTPS callback configuration, and an explicitly approved one-number call/SMS test. No credentials or paid traffic were available or used.
2. **Client/device acceptance:** the other team must validate the documented manual phone/code entry, cookie/bearer transport, mobile/web/portal UI, actual device app-presence reporting, and browser/device behavior. No frontend source or device code was changed in this backend-only stage.
3. **Production operations:** deploy trusted TLS, managed secrets, encrypted PostgreSQL/attachment backups, separated key management, off-host backup retention, and repeated restore drills under the deployment's approved KMS/platform. The local isolated backup/restore procedure was exercised; production controls are not claimed as provisioned.
4. **Explicitly deferred product extensions:** independent lost-phone recovery, QR UX, organization/government workflows, advanced spam classification/search, distributed infrastructure, and Internet SMTP interoperability remain outside this stage. Refresh-token rotation is implemented locally; see Stage 3 amendments. The API documents these boundaries rather than claiming support.
5. **Actual malware scanning:** scanner states and extension points are present, but uploads remain `unscanned`; no scanner or malware protection is claimed.

No locally implementable Stage 2 acceptance gate remains open. Provider/device and production acceptance must remain separate from that statement.
