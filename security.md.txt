Passwords are bcrypt-hashed and never returned. Login and registration issue signed JWT access tokens whose random jti is persisted in sessions; middleware checks that the session is active and not expired. Logout deletes the session. Mobile restoration preserves a token across network/server failures and clears it only after an authenticated 4xx response.

All database calls use PostgreSQL parameters. Conversation routes require authentication and verify membership. JSON request bodies are limited to 64 KiB, and CORS is configured by CORS_ORIGIN. JWT_SECRET and database credentials are environment variables. The Compose fallback secret is for local development only and must be replaced.

Aliases are restricted to non-phone names and reserved names, and do not claim ownership of an unverified phone number. Deactivated aliases stop receiving new messages; deleted alias addresses remain permanently reserved so historical conversations cannot be redirected to a new owner. Direct conversations group by stable account identity across primary-phone and alias addressing. Canonical phone addresses are only routable to registered active account ownership.

Bearer sessions remain supported for compatibility. Cookie sessions use HttpOnly Secure cookies in production, SameSite=Lax, and a separate CSRF cookie/token for writes. CORS is an explicit allowlist. Authentication attempts are limited per IP and submitted phone key (30 attempts per 15 minutes); this is a baseline local control, not a complete distributed abuse-prevention system. Passwords are rejected above 72 UTF-8 bytes before bcrypt.

Database failures during authentication are returned as temporary unavailability rather than invalid credentials. Access tokens expire after 15 minutes; opaque 32-byte refresh credentials are stored as SHA-256 hashes and the server retains generation history. Refresh sessions expire after 30 days. The immediately previous credential can recover an encrypted cached rotation response for a bounded 90-second window; later replay revokes only that session family. Bearer and HttpOnly-cookie renewal are supported; cookie renewal requires CSRF validation and conflicting cookie/body credentials are rejected. Logout, account suspension, and phone change revoke the applicable session family. Distributed rate limiting is not implemented. SMS/IVR signup, signed provider callbacks, app-presence-aware SMS notifications, and Twilio Verify/Messaging adapters are implemented and locally tested with fixtures; no live provider acceptance or external delivery is claimed.

Uploads are authenticated, stored outside static paths with opaque keys, limited to 10 MiB per file, and support range downloads with `nosniff` and sanitized filenames. Ready attachments are downloadable only by the sender or addressed recipient; staged uploads remain owner-only. Streaming limits and per-upload advisory locks are used; owner-only status supports resumable-offset reconciliation. Cleanup removes expired uploads and unreferenced files in bounded batches while preserving active chunk files and shared attachment references. Scanner state is explicit; files remain `unscanned` until a real scanner is integrated. Drafts are private to their owner and use revision conflicts. Sync cursors are account-scoped decimal strings; snapshot pages hand off to incremental sync only after the last page.

Local verification sends no real external email, SMS, call, or OTP. Telecom callback routes require Twilio's `X-Twilio-Signature` over the configured public URL and all POST form fields; the local `/api/otp/webhook` HMAC fixture remains a distinct mock protocol. Signed fixtures locally exercise SMS/IVR registration, outbox notifications, and provider status reconciliation, but no live provider success is claimed. Caller ID is not treated as independent phone ownership for recovery; IVR signup accounts begin without a phone-verified timestamp. Attachments remain `unscanned`; no active malware scanner or malware-clean guarantee exists.

Operations: `/live` reports process liveness without dependency checks; `/ready` verifies PostgreSQL and writable attachment storage. Request logs are structured and omit bodies, credentials, and query strings; responses carry `X-Request-ID`. `/metrics` exposes bounded request counters and aggregate outbox states. Outbox claims are capped, leased with fencing tokens, retried with bounded backoff, and terminal failures remain visible. External SMS sends are at-least-once across the provider-acceptance/response-loss window: callback deduplication and monotonic reconciliation do not make a remote provider call exactly once. Retention cleanup is scheduled and reports per-category counts; it removes expired sessions, OTP artifacts, idempotency records, snapshots, telecom records, terminal jobs and old sync events in bounded batches.

Coordinated backup/restore for the root Compose deployment (PowerShell; use the same Compose project and timestamp for both artifacts):

1. Choose a protected destination with enough free space. Set `$backupDir = Join-Path $HOME 'phonemail-backups'`, create it with `New-Item -ItemType Directory -Force $backupDir`, then set `$compose = 'docker-compose.yml'`, `$stamp = (Get-Date).ToUniversalTime().ToString('yyyyMMddTHHmmssZ')`, and `$dbFile = Join-Path $backupDir "phonemail-db-$stamp.dump"`. The storage command below uses the same timestamp for its artifact.
2. Quiesce API writes with `docker compose -f $compose stop backend`. Check `$LASTEXITCODE` after every Docker command; do not proceed if a step fails.
3. In the database container, run `docker compose -f $compose exec -T db sh -c 'pg_dump -Fc -U "$POSTGRES_USER" -d "$POSTGRES_DB" -f /tmp/phonemail.dump'`, then `docker compose -f $compose cp db:/tmp/phonemail.dump $dbFile`. Remove that temporary dump from the container after verifying the host artifact.
4. Resolve the Compose volume whose label is `com.docker.compose.volume=backend_storage` (for example, `docker volume ls --filter 'label=com.docker.compose.volume=backend_storage' --format '{{.Name}}'`). With that exact volume name in `$storageVolume`, archive it while read-only: `docker run --rm -v "${storageVolume}:/data:ro" -v "$($backupDir.Replace('\','/')):/backup" alpine:3.20 tar -czf "/backup/phonemail-storage-$stamp.tar.gz" -C /data .`.
5. Record the database and attachment archive as a matched pair. Encrypt both with the deployment's approved KMS/backup-encryption facility before off-host storage; keep decryption keys separate from the backup location. Restart writes with `docker compose -f $compose start backend` and verify `/ready`.
6. For restore, stop the backend, select a matched pair, restore the attachment archive into the same `backend_storage` volume and restore the database dump using `pg_restore --clean --if-exists` against the configured database. Start the backend, verify migrations/readiness, and exercise authorized attachment downloads and database/API reads before resuming traffic. Restore replaces current data and must be performed only under an approved recovery procedure.

These commands describe a consistent local Compose procedure, not a completed restore drill. Production must terminate HTTPS with a trusted certificate at the deployment edge and configure the exact public origin for CORS/provider signature validation; TLS protects transport but is not end-to-end encryption. Keep provider/database/JWT secrets in a deployment secret manager, rotate them under an operational runbook, and never put them in source or logs. Production encryption, key separation, off-host backup, and restore testing remain deployment responsibilities, not locally verified guarantees.
