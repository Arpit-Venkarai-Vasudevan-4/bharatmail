# Minimal backend contract proposals

These changes are **not implemented**. The frontend uses supported APIs where they preserve the existing thread and recipients. The current server rejects undeclared request fields, and its conversation-message send contract has no attachment references.

`POST /api/drafts/:id/send` already accepts `conversationId` and `attachmentIds`. The frontend uses it for a new ordinary message by the original sender when the initial message and its exact To/CC roles are available. Browser tests cover both direct and group conversations, attachment bytes for recipients, unchanged conversation/roles, and atomic draft consumption ([thread-contract-ui-results.json](thread-contract-ui-results.json)). Replies and server-routed sends from other members cannot use that path safely with the current contract.

## 1. Attach files to an existing conversation message

Extend `POST /api/conversations/:conversationId/messages` with optional `attachmentIds: string[]` (maximum 10), retaining the existing body, subject, `inReplyToId`, `Idempotency-Key`, and operation-lookup behavior. The server must derive the conversation membership and locked To/CC recipient roles from the existing conversation; the client must not supply a replacement recipient set. Validate that each upload belongs to the authenticated sender, is complete and ready, and is not already consumed by an incompatible message. Create the message, recipient copies, attachment links, mailbox state, sync event, and notification outbox entry in the same transaction. An older client omitting `attachmentIds` keeps current behavior. A failed validation or transaction leaves uploads available and creates no message.

Acceptance tests: attach a ready upload to a direct thread and a group thread; assert the message remains in the same conversation and membership/To/CC roles are unchanged; verify permitted recipients can download it and unrelated users cannot; reject incomplete, foreign, and over-limit upload IDs without creating a message; drop the first response and retry with the same idempotency key to get one message and one attachment link; reject a changed payload for a reused key.

## 2. Atomically send an existing reply draft

Extend `POST /api/drafts/:id/send` with optional `inReplyToId`, requiring the already-supported `conversationId` when present. Preserve `conversationId`-only requests for existing clients and new-message attachment sends. The draft's recipient IDs and To/CC roles must exactly match the server-locked reply recipients for that conversation and sender; reuse the routing rules of `POST /api/conversations/:id/messages` rather than adding participants. In one transaction, validate `If-Match`, draft ownership/revision, reply parent, one-reply constraints, and ready attachment ownership; create the reply and attachment links; consume the draft; and append mailbox, sync, and notification state. Existing requests without `inReplyToId` retain current behavior. Keep the current `Idempotency-Key` response and operation lookup semantics. A validation/transaction failure leaves the draft and uploads intact.

Acceptance tests: send a reply from a populated draft in a direct and group conversation; assert the same conversation ID and fixed membership/roles; assert attachments and draft consumption are atomic; prove a stale revision, foreign conversation, changed recipient roles, invalid reply parent, non-ready attachment, or second reply leaves no partial message and preserves the draft; drop the response and retry the same key to return one reply and one draft consumption.

Encrypted `POST /api/e2ee/messages` already supports `replyToId` and preserves its conversation. Encrypted draft send currently has no reply-parent field; the frontend therefore does not consume an encrypted reply draft as an atomic reply. Add a separately reviewed ciphertext-only encrypted draft-reply contract only if that workflow is required; it must keep the same locked recipient set, bind the reply parent and revision into the signed/idempotent operation, and pass the same atomicity and replay tests without exposing plaintext.

## 3. BCC privacy (not implemented)

Current ordinary and encrypted send schemas reject BCC. Do not map hidden recipients to To/CC or reuse visible conversation membership. The minimal safe extension is an optional `bcc` array on new ordinary drafts and new-message draft send only. Persist BCC membership privately per sender/message; never add BCC addresses to public `conversation_members`, `members`, To/CC projections, recipient-visible delivery status, sync payloads, search snippets, notification envelopes or reply-all routing. BCC recipients need authorized private mailbox copies and their own attachment access without learning other BCC recipients. The sender may see their BCC list. BCC replies must become explicit sender-only replies, without exposing the hidden role. If this cannot fit existing conversation projections, a separately reviewed private-copy model is required; this is not just a request-schema change. Existing clients omitting BCC retain existing behavior. Encrypted BCC requires separate cryptographic review: signed routing and recipient-key metadata must not disclose hidden membership; ordinary BCC approval would not enable encrypted BCC.

Acceptance: two visible and two hidden recipients; inspect every API projection and sync/notice/delivery path as each party; prove hidden addresses and counts do not leak; reply-all excludes BCC; unrelated/other-BCC users cannot access private copies; sender sees intended BCC; upload ownership, block/privacy checks and fixed visible membership remain enforced; same-key retries commit one logical send; changed hidden recipients conflict; validation failure preserves draft and uploads.

## 4. Forwarding and public metadata

The website now offers **Forward as new message** for ordinary mail using existing revisioned draft, upload, recipient confirmation and send routes. It adds sender/date/subject attribution to editable plain text and requires explicitly selected recipients. No original attachment references are reused: users must deliberately download and re-upload selected files under their own ownership. The composer explains that this is a new message with explicit recipients; the backend reuses an existing direct conversation for the same address pair and creates a new group for a new group send. A guaranteed fresh direct conversation is not supported. Encrypted messages do not expose ordinary Forward; a future encrypted-forward flow must explicitly choose encryption, reverify destination fingerprints and re-encrypt only the selected content/files. There is no automatic plaintext downgrade or claim that forwarded attribution proves original authorship.

List attachment badges use actual returned attachment metadata only. `conversationService.listConversations` selects `has_attachments` internally but its current response projection omits it; list APIs therefore cannot reliably show attachment indicators before content is opened. Minimal additive proposal: expose an authorized `hasAttachments:boolean` on each conversation and mailbox/search row, computed only over messages visible to that requesting account. Include encrypted-message policy explicitly (do not infer private MIME attachments from ciphertext). Omission remains unknown for old servers, never “no attachment.” Test message/draft ownership, deleted/trashed visibility, group membership and account-scoped sync/list parity. No per-row attachment downloads or full mailbox fetch are acceptable workarounds.

Private recipient confirmation intentionally returns no internal user ID. Encryption and blocking use the user's saved contact mapping or authorized encrypted routing data. Generic ID lookup must not be added merely for convenience. A future sender-block endpoint accepting an authorized conversation/message reference could allow blocking an unsaved sender without exposing IDs or enabling account enumeration; validate mailbox membership and derive sender server-side, with the same blocking semantics and audit/sync state.

## 5. OTP-only encryption key management

The actual `POST /api/e2ee/reauth` route accepts only `password` (`backend/src/routes/e2ee.ts:61`). Therefore OTP-only accounts cannot currently enroll/rotate/revoke through that reauthentication contract. The frontend explicitly explains this limitation; its disabled key-management controls are not counted as implemented OTP-only key management.

If required, minimally extend reauthentication with a mutually exclusive OTP proof form (`challengeId`, `code`) issued for a dedicated `e2ee_reauth` purpose bound to the authenticated immutable account, current verified phone and current session. Never accept a login or phone-change proof as an implicit substitute. Keep current password requests compatible. On successful one-time proof consumption, establish the same short-lived server reauthentication authorization already required for the signed key lifecycle; retain every public-key/signature/challenge check. Changes to OTP purpose issuance and `/api/e2ee/reauth` require backend/security review, not a frontend bypass.

Acceptance: unchanged password flow; legitimate OTP-only enrollment/rotation/revocation; wrong/expired/replayed/cross-account/cross-session/wrong-purpose proofs fail without key mutation; phone change revokes current key and prior reauthentication; local protected old keys can still read authorized historical mail; changed keys still require independent recipient fingerprint review. No OTP codes returned by production endpoints or placed in logs.

## 6. Authentication account capabilities and secure password lifecycle

Observed contracts: `POST /api/auth/register` creates a password-backed account without a phone-ownership proof; password login remains available independently of OTP provider state. OTP registration creates a null password hash. `loginWithOtp` in `backend/src/services/userService.ts:692` consumes a valid login proof but rejects accounts with a password hash. This rejection is now verified through the rendered UI with a legitimate local proof, not inferred from the capability advertisement. Password/OTP are alternatives for their supported account types, not mandatory two-factor authentication.

No secure user-facing password setup/change/reset route exists in this source. The frontend must not assign a password to an OTP account or promise reset/recovery. Minimal proposed additions, subject to owner/security review: authenticated `POST /api/auth/password/setup` for a passwordless account, bound to a fresh dedicated `password_setup` proof of that immutable account/current verified number/session; `POST /api/auth/password/change` with current-password proof for an account that already has a password; and a separately reviewed recovery request/confirm pair using dedicated short-lived one-use `password_reset` proofs, generic anti-enumeration responses, rate limiting and explicit session/key consequences. Apply the existing 6-character/72-UTF-8-byte policy without trimming; never reuse login/signup/phone-change proofs. Existing password login/register remain compatible. Password setup alone must not silently change the OTP policy: owner must choose and advertise account-appropriate methods explicitly without leaking account existence before proof.

Acceptance: set a password for a genuinely verified passwordless account and sign in with it; reject incorrect/expired/replayed/wrong-purpose/cross-account/session proofs; change password only after correct reauthentication; old password and revoked sessions fail; keep immutable identity, mailbox, drafts and protected key history; all rate errors include Retry-After; lost confirmation response has a documented replay/reconciliation outcome. Never return secrets in URLs/logs. A reset must not pretend it recovers a forgotten private-key passphrase or decrypts historical E2EE.

## 7. Inbound IVR registration activation and web sign-in

Existing signed provider routes are `POST /api/telecom/ivr/inbound` and `/api/telecom/ivr/decision`. The inbound prompt tells the caller to press 1 to consent/create an account and 2 to repeat. `backend/src/services/telecomService.ts` uses `mvp-1` and creates an undisclosed random password hash. Combined with the OTP restriction above, newly call-created accounts currently have no usable normal web sign-in method. No browser call endpoint or webhook bypass is implemented.

Before activating the public number, define an additive, reviewed IVR-account sign-in policy: either create explicitly passwordless, phone-verified IVR accounts eligible for the existing OTP login contract, or add secure password setup under proposal 6. Handle previously created IVR accounts explicitly; do not remove password hashes from normal password accounts. Advertise SMS/voice OTP availability only when configured, and ensure call-created accounts can request/consume a correctly purpose-bound normal login proof. Broad provider capability alone cannot prove this path works.

Provider setup remains backend-only: official dial-in number, valid signed webhook public URLs, backend credentials/signing verification, caller-number canonicalization, consent evidence and approved legal wording/version. The website uses only a validated public number and explicit activation/sign-in-readiness flags, both false by default. Outbound `channel=ivr` verification-code delivery is distinct from inbound registration and notification preferences. Local provider source reports voice supported but unconfigured; the UI keeps it unavailable. Controlled browser capability/error fixtures verify request shape only, never actual provider delivery.

Acceptance before activation: legitimate signed inbound/decision-1 sequence creates one canonical phone identity with recorded consent; decision-2 repeats without creating; missing/invalid signatures or absent consent create nothing; duplicate calls preserve existing account; a newly call-created account completes normal web login with a legitimate proof or approved password setup; existing password/OTP account methods remain compatible; actual production legal copy/version match; no auto-consent digits, browser webhook calls or client provider secrets. The configured website tel/copy/continuation checks are not acceptance of this provider/backend sequence.
