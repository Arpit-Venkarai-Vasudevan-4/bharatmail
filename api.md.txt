Base URL: http://localhost:3000. API routes are under /api. GET /live is process liveness and does not depend on services; GET /health is a legacy dependency check; GET /ready requires startup completion plus PostgreSQL and writable storage.

Authentication: POST /api/auth/register body {phone,password,displayName?,language?,termsAccepted:true,signupChannel?}; POST /api/auth/login body {phone,password}; POST /api/auth/logout and GET /api/auth/me require Authorization: Bearer token. GET/PATCH /api/me and address routes require auth. POST /api/me/addresses accepts a non-phone alias name only; it does not verify or reserve another user's phone identity.

Messaging: GET /api/conversations?filter=all|unread|attachments|favorites&q=...; POST /api/conversations body {participantPhones:[phone or PhoneMail address]}; GET /api/conversations/:id?page=1&pageSize=50; GET /api/conversations/:id/messages?page=1&pageSize=50; GET /api/conversations/:id/messages/:messageId loads a full authorized body on demand; POST /api/conversations/:id/messages body {body,subject?,to?,cc?,inReplyToId?}; PATCH /api/conversations/:id/messages/:messageId/state updates only per-user read/favorite/folder state; GET /api/conversations/mailbox/:folder?limit=20&cursor=... lists inbox, sent, drafts, trash, archive, or spam. Mailbox pages are bounded (maximum 100) and use stable owner/folder-bound keyset cursors. Drafts mailbox pages combine owner-private legacy message drafts and dedicated revisioned drafts and identify rows by `entityType`. Page 1 of conversation messages contains the latest messages and later pages contain older messages. One recipient reuses a direct thread; multiple recipients always create a group. Existing-thread To/CC identities and roles are server-locked. Unknown send/draft fields are rejected; BCC is not supported.

Errors use { "error": { "code": "...", "message": "...", "requestId": "...", "retryable": false } }; temporary failures include Retry-After. Every response includes X-Request-ID. Message pages are bounded to 100 items and are latest-first.

Authentication supports the existing bearer token contract and cookie mode by sending X-Auth-Transport: cookie on login/register. Cookie state uses the same persisted session, with a readable CSRF cookie and X-CSRF-Token required for state-changing requests. Configure exact origins in CORS_ORIGIN.

OTP authentication sequences are operation-specific. Request a signup challenge with `POST /api/otp/request` `{phone,purpose:"signup"}`, then submit `{phone,challengeId,purpose:"signup",code,termsAccepted:true,...}` to `POST /api/auth/otp/register`. Validate acceptance and profile fields before the server consumes the proof. Login uses `purpose:"login"` followed directly by `POST /api/auth/otp/login`; do not call `/api/otp/verify` first. That generic route rejects signup/login/phone-change purposes. Local challenge consumption and account/session creation commit in one database transaction; failed transactions can be retried with the same proof, while committed proof replay is rejected. Lost responses require a fresh login challenge. External Verify approval is first persisted as a durable, expiring grant bound to provider, phone, purpose, operation, and (for phone changes) account; provider timeouts are treated as ambiguous and require a fresh challenge. Local mock proofs set `phoneVerificationProvenance:"local_mock"` and do not set externally verified ownership.

Account continuity: `POST /api/auth/phone-change` requires an authenticated existing account and a fresh `phone_change` OTP for the proposed number. Password-backed accounts must also reauthenticate with `currentPassword`. OTP-only accounts must instead provide `oldChallengeId` and `oldCode` from a separate `phone_change_old` OTP issued to the current number; new-number proof alone is never accepted as proof of old-account ownership. Both OTP proofs are consumed atomically with the account/address/history/audit/sync/session update. Phone verification uses the provider recorded on the challenge, not the currently selected environment provider. The account UUID and mailbox are retained, the old address is reserved without forwarding, and old sessions are revoked. Clients may provide an `Idempotency-Key` (8-128 safe characters) to recover the exact encrypted response for 15 minutes after a lost response; recovery requires the same still-unexpired original bearer/cookie credential, key, and identical request body, and does not repeat the operation. Lost-old-phone recovery without an independent factor is unavailable.

Contacts and privacy: authenticated `GET/POST/PATCH/DELETE /api/me/contacts` provides private bounded contacts; listing accepts `q`, `limit` (1–100), and `offset`; `POST /api/me/recipient-confirmation` returns minimal discoverability-safe confirmation and is rate-limited; `GET/PATCH /api/me/preferences` controls discoverability, profile visibility, read receipts, communication, SMS, and IVR preferences. Communication-disabled, blocked, or inactive recipients cannot receive new sends; read receipts and profile data are filtered by the recipient's preferences. `GET/POST/DELETE /api/me/blocks` manages account-ID blocks. Blocks are enforced during conversation creation and message delivery and return a generic recipient-unavailable error; private block relationships are not exposed to the other account. `GET/POST/PATCH/DELETE /api/me/addresses` supports listing, creating, activating/deactivating and deleting owned aliases. Alias names must be non-phone local names and are globally unique; deactivated aliases stop receiving, and deleted aliases remain permanently reserved to protect historical authorization. `PUT/DELETE /api/me/profile-picture` associates/removes an owned ready upload, and authenticated `GET /api/users/:id/profile-picture` applies profile visibility.

Security events: authenticated `GET /api/me/security-events?limit=25` returns only the current owner's durable in-app notices (limit 1–50); `PATCH /api/me/security-events/{id}/read` marks an owned notice read and returns 404 for another account's notice. Existing operations create transactional audit entries for account creation, accepted phone proof, successful login/logout, coalesced known-account failed authentication, phone change, alias lifecycle, security/privacy-setting changes, message deletion, and detected refresh-credential replay. Applicable high-risk operations also create durable in-app notices in the same transaction; notification failure rolls back the triggering success. Metadata is allowlisted and excludes phone/address strings, credentials, OTP values, message content, and IP-based device claims. Failed-auth events are coalesced per known account for five minutes; unknown identities do not create account-linked rows. Successful idempotent recovery does not duplicate completion events. Audit and notice rows are cleaned in bounded batches after 365 days (operational retention, not legal-compliance policy). Account recovery, administrator action, account deletion, and device-recognition events have no implemented trigger.

POST /api/conversations/:id/messages accepts Idempotency-Key (8-128 printable characters). A successful key is retained for 24 hours; GET /api/conversations/operations/:key returns the durable resource identity for authenticated reconciliation. Reusing a key with a different payload is a conflict.

GET `/api/capabilities`, GET `/api/telecom/capabilities`, and GET `/api/otp/capabilities` distinguish supported, configured, simulated, and live-tested telecom capabilities (the OTP endpoint also separates verification from notification capabilities). Unconfigured local SMS notification work is recorded as `simulated`, never as provider acceptance. `POST /api/telecom/sms/inbound`, `/ivr/inbound`, `/ivr/decision`, and `/messaging/status` are public server-to-server callbacks and require `application/x-www-form-urlencoded` plus a valid `X-Twilio-Signature`. Signature verification uses `TWILIO_AUTH_TOKEN`, every received form field, and the exact URL reconstructed from `TWILIO_PUBLIC_URL` plus the request path/query; request Host and forwarded headers are not trusted. Inbound SMS uses Twilio-signed `From`, `AccountSid`, `To`, and `MessageSid`; `JOIN YES` is explicit terms consent, `JOIN` returns instructions, and `STOP` disables SMS preferences for the associated account. Voice Gather presses consent only on digit 1; digit 2 repeats, invalid input is bounded, and empty input times out without creating an account. These callbacks are separate from the local HMAC `/api/otp/webhook`.

Phone signup through inbound SMS requires `JOIN YES`; voice signup begins at the inbound call hook and only creates on the signed Gather consent. Existing-account callbacks never replace credentials. IVR Caller ID is not treated as independently verified phone ownership; SMS signup is tied to a signed inbound SMS, and OTP verification remains the account login proof. SMS notification text is exactly “You have received an email from <Sender>. Subject: <Subject>.”; message bodies are not sent. Notifications are queued transactionally and sent only to active recipients whose SMS preference is enabled and mobile-app presence is false. Local unconfigured sends become `simulated`. A Twilio callback monotonically reconciles accepted/sent/delivered/failed state; external send retries cannot promise exactly-once delivery if Twilio accepted a request but the response was lost.

App presence is mutable: authenticated `POST /api/me/app-presence` marks the app present; `PUT /api/me/app-presence` accepts `{present:boolean}` to update either direction.

Provider activation checklist:

* Set `OTP_PROVIDER`, `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_API_KEY_SID`, `TWILIO_API_KEY_SECRET`, `TWILIO_VERIFY_SERVICE_SID`, `TWILIO_PHONE_NUMBER`, `TWILIO_MESSAGING_SERVICE_SID`, `TWILIO_APPROVED_TEMPLATE_SID`, `TWILIO_PUBLIC_URL`, and `TWILIO_TIMEOUT_MS` as required by the enabled provider features. Keep credentials in deployment secret storage.
* Provision an approved Twilio account, permitted SMS/voice sender or Messaging Service, Verify service if OTP is enabled, and an approved Content template with `{{1}}` sender and `{{2}}` subject variables if fallback is enabled.
* Configure POST `${TWILIO_PUBLIC_URL}/api/telecom/sms/inbound` for incoming SMS and `${TWILIO_PUBLIC_URL}/api/telecom/ivr/inbound` for incoming voice. The Voice `<Gather>` callback path is `/api/telecom/ivr/decision`; status callbacks are generated as `/api/telecom/messaging/status?deliveryId=<UUID>`.
* Serve callbacks over public HTTPS with a trusted certificate. `TWILIO_PUBLIC_URL` must be the externally configured origin; signature verification includes the full path/query and all form parameters.
* A future authorized one-number test must be explicitly approved, use a provider-permitted number, verify request and callback state, and then disable/remove the test configuration. No number purchase, free access, or live test is implied.

Stage 2 endpoints: GET/POST/PATCH/DELETE `/api/drafts` are private draft operations. PATCH accepts `If-Match: "revision-N"` and returns `REVISION_CONFLICT` on stale edits. Start synchronization with `GET /api/sync/snapshot?limit=50`. The server materializes a repeatable-read current-state snapshot, including profile/preferences, active addresses/aliases, all owner drafts, contacts, outgoing blocks, authorized conversations/messages/per-user state/attachment metadata, and staged/ready upload metadata; the snapshot is not reconstructed from retained event history. Consume `records` in pages; while `hasMore` is true, request `/api/sync/snapshot?snapshotId=<id>&cursor=<nextCursor>&limit=50`. Do not switch to incremental sync until the final page supplies `incrementalCursor` (the snapshot watermark). BIGINT watermarks, record counts and cursors are decimal strings; do not parse them as JavaScript numbers. Snapshot pages are immutable, account-scoped, bounded to 100 records per response, and expire after 24 hours; `SNAPSHOT_EXPIRED` requires a new snapshot. Apply later `GET /api/sync?cursor=<incrementalCursor>&limit=50` pages in order; `action:"deleted"` records are tombstones. `CURSOR_EXPIRED` indicates retained events no longer cover the requested cursor and requires a fresh state snapshot. A failed/unauthorized snapshot ID returns 404. Per-account event locks serialize revisions with commit and pruning. POST `/api/uploads` accepts an authenticated stream with `X-Filename` and `X-Expected-Bytes` (1-10 MiB); the default per-file limit is 10 MiB, per-user quota is 50 MiB, and three staged uploads may be active concurrently. Owner-only `GET /api/uploads/:id/status` reconciles a resumable offset/status after a lost response; `GET /api/uploads/:id` supports authenticated byte ranges. Upload IDs and storage keys are opaque.

Resumable uploads use `X-Upload-Mode: resumable` to create a staged upload, then PATCH `/api/uploads/:id` with `X-Upload-Offset` chunks until the expected offset marks it ready. A wrong offset returns `UPLOAD_OFFSET_CONFLICT`; concurrent writers for one upload are serialized by a database advisory lock. Streaming byte limits reject excess bytes before they are retained, and a retry truncates uncommitted file tails back to the committed offset before applying the next chunk. MIME is inferred from recognized signatures and otherwise becomes `application/octet-stream`; the client declaration is not trusted. `scannerState`/`scanStatus` is currently `unscanned`; the schema allows `pending`, `clean`, and `rejected` for a future actual scanner. No malware scanning/protection is claimed. Cleanup removes expired staged uploads and unreferenced files; attachment-shared files are retained.

The authenticated download URL is `GET /api/uploads/:id`, where `id` may be an owner upload ID or a delivered attachment ID; sender and addressed recipients only are authorized. Single ranges support suffix, open-ended, and clipped end values and return `Content-Range`. Credentialed browser clients must use an exact origin from `CORS_ORIGIN` and allow `Content-Type`, `Authorization`, `X-Auth-Transport`, `X-CSRF-Token`, `Idempotency-Key`, `If-Match`, `If-None-Match`, `X-Request-ID`, `X-Filename`, `X-Expected-Bytes`, `X-Upload-Mode`, `X-Upload-Offset`, and `Range`. Exposed response headers include `Retry-After`, `X-Request-ID`, `ETag`, `Content-Range`, `Content-Length`, `Content-Disposition`, and `Accept-Ranges`. The API does not trust forwarded-host headers for provider callbacks.

Atomic `POST /api/drafts/:id/send` requires the owner, `If-Match: "revision-N"` and `Idempotency-Key`. It validates recipients and ready attachment ownership in the same transaction as message, recipient-copy, mailbox-state, sync and notification-outbox writes. A retry with the same key returns the original message; a changed payload conflicts, and a failed transaction leaves the draft intact.

The outbox worker claims jobs with a lease token, retries failures with a bounded attempt count, and fences stale workers; unknown job kinds fail rather than being treated as sent. OTP challenges are purpose-bound, expiring, single-use and attempt-limited, with durable phone/IP request limits and recipient-confirmation limits. `/api/otp/webhook` uses a generic local HMAC fixture format and is not Twilio request validation. Twilio-signed telecom callbacks and SMS workflows are locally fixture-tested only; SMTP delivery and exactly-once provider delivery are not implemented or claimed.

Stage 1 security contract: password signup requires `termsAccepted:true`; both registration endpoints accept optional `termsVersion:"mvp-1"` and persist the current version/acceptance timestamp. Unsupported language/source fields and stale terms versions are rejected. Passwords are limited to 72 UTF-8 bytes before bcrypt hashing. Password login/signup rate limits use durable HMAC-keyed PostgreSQL buckets shared across API instances (30 requests per canonical phone and 120 per IP in 15 minutes); OTP phone/IP limits and resend reservations are durable as well, return the measured `Retry-After`, and have indexed cleanup of expired rows.

External Twilio Verify checks use the exact persisted verification SID (`VerificationSid`), not a phone-only lookup that could select a reissued challenge. On provider approval, the API stores a bounded authorization grant and a keyed hash of the approved code. This allows a retry after a local database rollback only with the same approved code and operation binding; the grant is consumed with account/session creation. Provider timeouts, interrupted checks, or failure to persist approval remain ambiguous and fail closed. No test run sends provider traffic.

Legacy unsent `messages.folder='drafts'` are visible to their sender only. Snapshot materialization includes an owner's own draft content and attachments but excludes another participant's unsent message draft; incremental message events, message search/details, and recipient attachment downloads enforce the same boundary. Sync retention checks and event-page selection serialize with pruning on the account stream lock, returning a complete page or `CURSOR_EXPIRED`.

Phone numbers are digit-normalized without inferring a country prefix. Phone changes and new-number claims serialize on a per-canonical-number advisory lock; `phone_history` is a permanent non-routable reservation, enforced by application checks and address/history triggers. Direct conversation lookup uses stable account IDs so an alias and a primary phone address for the same person reuse the same direct conversation. Account UUIDs and stable message recipient user IDs remain unchanged. Local mock verification is provenance only and does not establish independent telecom ownership; number recycling remains a limitation.

## Manual client sequences and transport

Password account: `POST /api/auth/register` with `termsAccepted:true`, then retain the returned bearer `token` and opaque `refreshToken` or request `X-Auth-Transport: cookie`; later login uses `POST /api/auth/login`. Access tokens expire after 15 minutes; the refresh session lasts 30 days. Renew with `POST /api/auth/refresh` and `{refreshToken}` for bearer transport, or the HttpOnly refresh cookie for cookie transport. Cookie renewal requires the CSRF cookie value in `X-CSRF-Token`; conflicting cookie and body credentials are rejected. A retry of the immediately previous refresh credential returns the same encrypted response for at most 90 seconds to recover a lost response; later replay revokes only that session family. OTP account: `POST /api/otp/request` with the phone and purpose, let the server/provider deliver the code, then accept manual phone/code entry and call the operation route directly: signup uses `POST /api/auth/otp/register` with `purpose:"signup"` and terms consent; login uses `POST /api/auth/otp/login` with `purpose:"login"`. Do not call `/api/otp/verify` first for signup/login. Phone change requires an authenticated existing session and fresh new-number proof; password accounts also reauthenticate by password, while OTP-only accounts require separate old-number and new-number proofs. Automatic SIM/OTP reading, IVR device UI, web-browser permission prompts, and portal form behavior are unsupported frontend features; users must be able to enter numbers and codes manually.

## Shared errors, pagination, revisions, and safe retry

* `400` means malformed/invalid input; `401` means missing, invalid, expired, or revoked authentication/provider signature; `403` means an authenticated operation is denied by CSRF, account status, recipient privacy, block, or communication policy; `404` deliberately hides private or unavailable resources; `409` means an identity, thread-recipient, idempotency, reply, upload-offset, or draft-revision conflict. `410` means an expired/retention-truncated synchronization cursor or snapshot and requires snapshot recovery. `413` is a body/upload limit; `416` is an invalid byte range; `428` means required draft-send `If-Match` was omitted; `429` is a rate/quota limit. Errors use `error.code`, `message`, `requestId`, and `retryable`; retryable failures and throttles may include `Retry-After`. Transient 5xx should be retried only with the same operation key where supported; do not turn 4xx conflicts into blind retries.
* Conversation and message-history pagination uses bounded limits (at most 100); page one is newest and later pages move backward by stable creation time/ID. Conversation summaries and mailbox rows are small; fetch full bodies and authorized attachments on demand. Search applies authorization and filter predicates before keyset pagination and covers historical messages. Contact pages use `limit` (at most 100) and `offset`.
* Send-message idempotency is optional but recommended for network retries; draft-send requires `If-Match: "revision-N"` and `Idempotency-Key`. Phone-change `Idempotency-Key` enables exact response recovery for 15 minutes with the same still-valid original credential and identical request body. Keys are account-scoped; reuse with changed content returns 409. External provider acceptance followed by a lost response can still duplicate a remote SMS; delivery callbacks do not provide exactly-once semantics.
* Snapshot pages are materialized and immutable. `snapshotId` plus `cursor` is the snapshot paging cursor; `incrementalCursor` appears only on the final page and is a separate handoff cursor. Watermarks/counts are decimal strings and must not be converted to JavaScript numbers. Local bounds are 10,000 records per snapshot, five active snapshots/account, five snapshot creations/minute, and 600 snapshot page requests/minute. Snapshot expiry or retention reset requires a new snapshot.

## Error and CORS headers

Every response carries `X-Request-ID`. With credentialed browser access, `CORS_ORIGIN` is an exact comma-separated origin allowlist. Allowed request headers are `Content-Type`, `Authorization`, `X-Auth-Transport`, `X-CSRF-Token`, `Idempotency-Key`, `If-Match`, `If-None-Match`, `X-Request-ID`, `X-Filename`, `X-Expected-Bytes`, `X-Upload-Mode`, `X-Upload-Offset`, and `Range`. Exposed headers are `Retry-After`, `X-Request-ID`, `ETag`, `Content-Range`, `Content-Length`, `Content-Disposition`, and `Accept-Ranges`. Cookie transport uses an HttpOnly session cookie, SameSite=Lax, Secure outside development, and a readable CSRF cookie; state-changing cookie-authenticated calls send the CSRF cookie value in `X-CSRF-Token`. No wildcard credentialed CORS is enabled.

## Supported and unsupported boundaries

`GET /api/capabilities`, `/api/otp/capabilities`, and `/api/telecom/capabilities` report support, configuration, simulation, and live-test evidence separately. For Twilio Verify set `OTP_PROVIDER=twilio`, `TWILIO_VERIFY_SERVICE_SID`, and either account SID/auth token or API-key SID/secret. Enable signed SMS/IVR callbacks with `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, and `TWILIO_PUBLIC_URL`; enable outbound SMS additionally with `TWILIO_PHONE_NUMBER` or `TWILIO_MESSAGING_SERVICE_SID`. `TWILIO_APPROVED_TEMPLATE_SID` enables only the approved template fallback; `TWILIO_TIMEOUT_MS` bounds adapter calls. Disabled providers do not require credentials. Production callback origins must be HTTPS and match the provider-configured public URL semantics.

External Internet SMTP delivery, BCC, independent lost-phone recovery, malware scanning, automatic OTP reading, and `/api/v1` routing are not implemented. Refresh-token rotation is implemented for both bearer and cookie authentication as described above. Message creation success means server-side mailbox commitment/queueing, not external provider acceptance or delivery. Attachment scan state is currently `unscanned`.
